bad_apple, but it's the cemetery

You asked for a server-streamed canvas-style animation, modeled on the bad_apple example from data-star.dev. This page explains exactly what got built, the wire it travels on, and the one gotcha that bit us along the way.

01 the bad_apple pattern

bad_apple is a one-trick example with a surprisingly small surface area. The server reads a precomputed video of ASCII frames off disk and pushes one frame every ~33 ms over an SSE connection. The client is just this: 

<pre data-signals="{_contents: ''}" data-text="$_contents"></pre>

That's the whole UI. Three Datastar attributes:

  • data-signals declares a reactive signal _contents, initialized to "". The leading underscore is a Datastar convention meaning “local UI state, don't persist or sync.”
  • data-text binds the element's text content to that signal — whenever $_contents changes, the <pre> re-renders.
  • (In bad_apple, some sibling element fires an @get to kick off the SSE stream that drives _contents.)

The clever bit isn't on the client. It's that the server, having opened an SSE response, just keeps pushing datastar-patch-signals events at 30 fps for the entire run of the animation. Each event sets _contents to the next ASCII frame. Datastar's client library merges those signals into the store, the data-text binding fires, the <pre>'s text content swaps. That's the loop.

02 what we built, end to end

Three pieces:

    browser                            go server
    ───────                            ─────────
    GET /demo/logo          ────►      DemoLogoPage    ► HTML w/ <pre>
                                       (one-shot render)

    GET /demo/logo/updates  ────►      DemoLogoUpdates ► SSE, ticks 30/sec
    (fired by data-init)               │
                                       ├─ frame 0  ────►  patch _contents
                                       ├─ frame 1  ────►  patch _contents
                                       ├─ frame 2  ────►  patch _contents
                                       └─ …

The first GET serves the page. The second GET is the long-lived stream — it never closes (until you navigate away). On every tick, the server marshals one signal patch and writes it to the response, the browser sees a new SSE event, Datastar applies it.

03 the markup

internal/views/demo_logo.templ 
<pre
    id="logo"
    data-signals="{_contents: ''}"
    data-text="$_contents"
    data-init="@get('/demo/logo/updates')"
    style="position: absolute; top: 48px; bottom: 40px; ..."
></pre>

Four attributes do all the work:

  • data-signals — declare _contents, initial value "". If we left this off, Datastar would still implicitly create the signal the first time the server patched it, but declaring it up front is clearer.
  • data-text — bind the <pre>'s text content to $_contents. Reactive: every signal patch triggers a re-render.
  • data-init — runs once when Datastar finishes initializing the element. We use it to fire @get, which opens the SSE connection.
  • style — just pins the <pre> between the navbar and footer so the streamed text fills the viewport.

04 the handler

internal/handlers/demo_logo.go 
func DemoLogoUpdates(w http.ResponseWriter, r *http.Request) {
    sse := datastar.NewSSE(w, r)               // opens text/event-stream
    ticker := time.NewTicker(time.Second / logoFPS)
    defer ticker.Stop()

    ctx := r.Context()
    start := time.Now()

    for {
        select {
        case <-ctx.Done():                       // client disconnected
            return
        case now := <-ticker.C:
            frame := renderMockLogoFrame(now.Sub(start).Seconds())
            if err := sse.MarshalAndPatchSignals(map[string]any{
                "_contents": frame,
            }); err != nil {
                return                              // write failed, bail
            }
        }
    }
}

The shape is the entire point of SSE-driven Datastar:

  1. Open the stream. datastar.NewSSE(w, r) sets the right headers (Content-Type: text/event-stream, Cache-Control: no-cache, etc.) and returns a helper that knows how to format Datastar events.
  2. Loop forever. Don't return. Each tick of the ticker is one frame.
  3. Marshal & patch. MarshalAndPatchSignals(map) turns the Go map into JSON, wraps it in a datastar-patch-signals event, writes it to the response, flushes. One method call = one frame on the wire.
  4. Watch the context. When the client closes the tab or navigates away, r.Context().Done() fires — that's how we know to stop tickling.

05 the wire format

If you curl -N http://localhost:8080/demo/logo/updates you'll see this, repeating every ~33 ms:

event: datastar-patch-signals
data: signals {"_contents":"=++*###%%%%%%%###***+++========...\n=++**####%%%######***+++==..."}

event: datastar-patch-signals
data: signals {"_contents":"=++**###%%%%%%%###***+++========...\n=++***####%%######***+++==..."}

event: datastar-patch-signals
data: signals {"_contents":"=++**####%%%%%%###***++++========...\n=++***####%%######***+++==..."}

That's the entire protocol. Two-line records:

  • event: tells the client which kind of patch this is. There are exactly two in Datastar v1: datastar-patch-signals (merge into signal store) and datastar-patch-elements (morph DOM). If you ever see datastar-merge-fragments, that's pre-v1 and dead.
  • data: is the payload. For signals, it's the literal word signals followed by a JSON object that gets deep-merged into the client's signal store. Setting a key to null would remove it.

The browser's EventSource receives those records, Datastar's client library dispatches each to its handler, the signal store updates, and any element bound to that signal (via data-text, data-show, data-class, data-attr, etc.) re-renders. Same engine that drives buttons, forms, and everything else — we just feed it from the server at 30 Hz.

06 the gotcha that cost us five minutes

data-on:load doesn't fire on a <pre>

First pass used data-on:load="@get(...)". The page rendered — navbar and footer showed up — but the body was a black void. DevTools showed only two requests: the page and datastar.js. No /demo/logo/updates request was ever fired.

Why: data-on:NAME attaches a listener for the native DOM event named NAME. The load event only fires on a handful of elements — window, <body>, <img>, <iframe>, <script>, <link>. Not <pre>. So the listener attached fine and then sat there, dormant, forever.

The fix is data-init:

// before (silent failure on <pre>):
data-on:load="@get('/demo/logo/updates')"

// after (always fires once, any element):
data-init="@get('/demo/logo/updates')"

data-init is Datastar's “run this expression exactly once when I take ownership of this element.” It doesn't care what kind of element — it fires during Datastar's own initialization pass, before any DOM event would have had a chance. For one-shot mount triggers, it's the right thing.

Rule of thumb: if you want “fire on real DOM events” (click, input, submit, focus, even load on elements that have one), use data-on:event. If you want “fire once when this element comes alive in Datastar's eyes,” use data-init.

07 a quick note on frame content

What's actually being streamed right now is a placeholder — an 80×28 grid where each cell picks a glyph from " .·:-=+*#%@" based on a two-sine-wave function of x, y, and t. It looks like flowing tidal lines, which is fine for proving the pipe works but isn't the cemetery logo.

The real fire.js logo — cell grid, baked logo bitmap, randomized cross/grave placement, responsive tier sizing — lives in ~960 lines of JavaScript. Porting it to Go is the next step. Once it's in Go, the only thing that changes is the contents of renderMockLogoFrame; the wire, the markup, and the handler shape all stay the same.

08 things you'll want to keep in mind

  • All signals get sent on every action. When data-init fires @get, Datastar serializes the whole signal store into the URL's query string. Right now _contents is "" at that moment, so it costs nothing. But if the SSE drops and Datastar reconnects, the last frame (~2.5 KB) would end up in the URL. If that matters: add {filterSignals: {exclude: /^_contents$/}} to the @get call.
  • Backpressure is on you. If a slow client can't drain frames as fast as the server writes them, the response buffer fills up. MarshalAndPatchSignals will eventually return an error and we bail. For a 30 fps text stream on a local network this won't matter, but a real production version would want to drop frames rather than block.
  • One handler = one goroutine = one client. Per-connection sim, as you picked. Each visitor gets their own ticker. If you ever want everyone to see the same frame at the same time, the sim moves into its own goroutine and the handler subscribes to a channel.
  • The <pre>'s id matters less than you'd think. Because this is a signal patch (not an element patch), Datastar isn't morphing anything by id — it's just updating a text node bound via data-text. The id="logo" is just for our own debugging.
