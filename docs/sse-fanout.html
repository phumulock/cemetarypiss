SSE fan-out & compression

How the lightning + ASCII-fire streams went from ~3.6 MB/s per client to ~242 KB/s per client — while server-side CPU dropped from O(N clients) to O(1).

01 the problem

The /demo/cmlogo page paints two animated layers on the server and pushes them to the browser over Server-Sent Events:

  • Lightning — a 720 × 180 ASCII grid (~130 KB per frame, mostly spaces with a few jagged bolts) at 20 fps.
  • Fire — two 1200 × 28 Doom-fire strips (~67 KB combined) at 16 fps.

With the original handler, every connected client got their own handler goroutine, their own random-number generator, their own grid buffer, their own strings.Builder, and their own uncompressed write loop. With N viewers, everything ran N times in parallel on a 256 MB / 1 vCPU Fly machine.

Two things made this expensive: the per-client recomputation (every viewer triggered its own RNG-driven simulation), and the raw bytes on the wire (a 130 KB grid that's 99%+ spaces was being shoved through TCP verbatim).

02 two changes

change 1 — one producer, many subscribers

The streams are pure RNG noise — nobody sees the “same” bolt twice anyway, and there's no per-user state. So every viewer can watch the same randomness without losing anything visually. One goroutine ticks, renders one frame, and broadcasts that single rendered string to every subscriber.

change 2 — compression on the SSE response

Datastar's Go SDK ships a one-liner: pass datastar.WithCompression() to datastar.NewSSE(...) and it negotiates gzip/brotli/zstd with the client and wraps the response writer. SSE is just text/event-stream over HTTP/1.1 chunked transfer, so the standard Content-Encoding path works fine.

The wins are huge here because the lightning grid is mostly spaces — a textbook case for entropy coding. A 130 KB frame of 99% spaces and a few jagged /|\* shrinks to under 1.4 KB.

04 how the hub works

Each stream has its own hub. The hub is a tiny wrapper around a map of subscriber channels, a mutex, and a flag for whether the producer goroutine is currently alive. 

type lightningHub struct {
    mu      sync.Mutex
    subs    map[chan lightningFrame]struct{}
    running bool
}

var globalLightningHub = &lightningHub{subs: make(map[chan lightningFrame]struct{})}

subscribe

When a client connects, the handler asks the hub for a channel. The hub adds it to the set; if the producer wasn't already running, it starts. 

func (h *lightningHub) subscribe() chan lightningFrame {
    ch := make(chan lightningFrame, 2) // buffer of 2 — see below
    h.mu.Lock()
    h.subs[ch] = struct{}{}
    start := !h.running
    if start { h.running = true }
    h.mu.Unlock()
    if start { go h.run() }
    return ch
}

broadcast

The producer renders one frame, then walks the subscriber set sending the same value to each channel. The send is non-blocking — if a subscriber's buffer is full, the producer drops that frame for that subscriber and moves on. The producer never stalls.

Dropping is safe because each frame is independent — there's no diff or delta that depends on the previous frame, so missing one just means a brief stutter instead of corruption.

lazy stop

At the top of every tick the producer checks whether the subscriber set is empty. If it is, it clears running and returns. An idle server burns no CPU on fire or lightning. The next subscriber that comes in restarts it. 

for range ticker.C {
    // ... compute frame ...

    h.mu.Lock()
    if len(h.subs) == 0 {
        h.running = false
        h.mu.Unlock()
        return
    }
    for ch := range h.subs {
        select {
        case ch <- frame:
        default: // slow consumer — drop this frame
        }
    }
    h.mu.Unlock()
}

the handler shrinks to nothing

All the simulation, allocation, and rendering moved into the producer, so the per-client handler is just “subscribe, forward, unsubscribe.” 

func DemoCMLogoUpdates(w http.ResponseWriter, r *http.Request) {
    sse := datastar.NewSSE(w, r, datastar.WithCompression())
    ctx := r.Context()

    ch := globalLightningHub.subscribe()
    defer globalLightningHub.unsubscribe(ch)

    for {
        select {
        case <-ctx.Done():
            return
        case frame := <-ch:
            if err := sse.MarshalAndPatchSignals(map[string]any{
                "_lightning": frame.grid,
                "_flash":     frame.flash,
            }); err != nil {
                return
            }
        }
    }
}

05 the freebies

While the producer was being lifted out, three micro-wins came along for free inside the lightning loop:

  • Grid switched from [][]rune to [][]byte. Every bolt glyph (/, |, \, *) is 1-byte ASCII, so storing rune (4 bytes) was pure waste — 4× memory cut on the largest hot buffer.
  • The grid is now allocated once at producer start and wiped between frames instead of make([][]rune, 180) + 180×make([]rune, 720) per frame. At 20 fps that's 3,620 fewer allocations per second.
  • The strings.Builder is reused via sb.Reset() instead of being a fresh value each tick.

None of these would have mattered when the work ran per-client — the wins are multiplied by the producer being centralized, since the savings happen once regardless of viewer count.

06 trade-offs & edge cases

everyone sees the same noise

With one producer, viewers connected at the same moment see identical bolts. For RNG-driven decorative animation this is fine — arguably better, because two people on a phone call now share the same stage. If the streams ever became per-user (a personalized logo, a name baked into the bolts), the per-client handler would have to come back.

slow consumers lose frames, not connections

A subscriber on a 2G phone won't backpressure the producer or block other viewers — they'll just miss a frame here and there. At 20 fps a dropped frame is invisible.

compression costs CPU per connection

The compress step still happens N times (once per SSE writer). Gzip on 1–5 KB/frame is cheap, but on a 1 vCPU box with hundreds of viewers it adds up. If that ever bites, the next step is to gzip the frame once in the producer and write the same byte slice to every subscriber's raw http.ResponseWriter — possible because every client gets the exact same payload.

fly's idle behavior still works

fly.toml uses auto_stop_machines = "stop" and min_machines_running = 0. When the last SSE connection drops, the producer exits, the handler returns, the HTTP keep-alive eventually idles, and Fly stops the machine. No background goroutine keeps the box warm.
