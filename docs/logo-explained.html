// the logo

how the cemetery assembles itself out of the dark

This is the landing-page logo — the ASCII skull that flies in piece by piece on a black field, with pixel-fire licking the top and bottom edges and two tracks of doom ambience underneath. It is entirely client-side: no server, no SSE, no Datastar. (That other thing, the server-streamed /demo/logo page, is a separate experiment — see logo-stream-explained.html.)

All of it lives in one file of vanilla JavaScript, no dependencies. The markup is just a stack of <canvas> elements plus a navbar/footer.

static/fire.js — mirrored inline in index.html 
<canvas id="c"></canvas>                // the big ASCII logo
<canvas id="fire-top"    ...></canvas>   // doom-fire strip, flipped
<canvas id="fire-bottom" ...></canvas>   // doom-fire strip, upright

The script splits into three independent self-invoking blocks (IIFEs):

    block 1   the ASCII logo fly-in        (canvas #c)
    block 2   two pixelated fire strips    (canvas #fire-top / #fire-bottom)
    block 3   wired into block 1's tail    audio: cross-fading background tracks

01 the baked logo bitmaps

The skull isn't drawn with paths. It's a pre-rendered ASCII bitmap — an array of equal-length strings where each character is one cell of art, drawn from the density ramp @ % # * + = - : . (space). @ is the darkest/solid fill; a space is empty.

There are three of them — LOGOS.small, .medium, .large — baked at different resolutions. Each is just rows of text: 

const LOGOS = {
  large:  ["@@@@@@@@@@...##**@@@%@@@@...", "@@@@@@...#+-=*+==+-=*%%@...", ...],  // ~49 rows
  medium: [...],
  small:  [...]
};
only the large bitmap is ever used

Despite three baked sizes, applyTierConfig() hard-assigns LOGO = LOGOS.large at every breakpoint — “always use the high-detail large logo so chars render finer at every breakpoint.” The smaller bitmaps are kept around but not rendered. Responsiveness comes from cell size, not from swapping the art.

02 responsive tiers

pickTier() reads window.innerWidth and returns one of three labels: 

function pickTier() {
  const w = window.innerWidth;
  if (w < 600)  return 'small';
  if (w < 1000) return 'medium';
  return 'large';
}

The tier doesn't pick a bitmap — it tunes layout numbers: navbar/footer heights, how much vertical space the logo should fill (vfill = 0.62 / 0.65 / 0.88), the corner-rounding radius, and the parameters of the cross system below.

03 building the grid

buildGrid() turns the viewport into a fixed grid of monospace cells and decides what character lives in each. First it sizes a cell so the logo fits: 

const availH = window.innerHeight - NAVBAR_PX - FOOTER_PX;
cellH = (availH * vfill) / LOGO_ROWS;   // height to fill the target fraction
cellW = cellH / 1.8;                    // monospace glyphs are ~1.8× taller than wide

// if that overflows horizontally, shrink to fit the width instead
if (LOGO_COLS * cellW > availW * 0.94) {
  cellW = (availW * 0.94) / LOGO_COLS;
  cellH = cellW * 1.8;
}

From the cell size it computes totalCols × totalRows covering the viewport, centers that grid vertically (gridYOffset), and positions the logo bitmap so it's horizontally centered and parked at the right height (logoColOffset, logoRowOffset). Every cell is then classified into one of a few kinds:

  • logo glyph — the cell falls inside the bitmap rectangle: take the character straight from LOGO[lr][lc].
  • space — a blank inside the bitmap.
  • deep fill — a logo @ whose eight neighbours are also @ (i.e. solid interior, not an edge). Flagged for the shimmer effect later.
  • outer filler — everything in the black field outside the bitmap, given a pseudo-random glyph from @%#&.
  • cross texture — a cell carved out by the cross system (next section).

The glyphs are deterministic, not Math.random() — fillerChar(seed) and textureChar(tier, seed) hash a per-cell seed through a sine so the same cell always gets the same character across rebuilds.

04 the hanging crosses

There's an elaborate sub-system that places upside-down crosses cascading below the logo. CROSSES is a bank of cross shapes (each a 2-D array of 0/1 at increasing sizes). CROSS_LEVELS describes rows of them — size range, vertical offset, count. placeCrossesInRegion() walks left-to-right packing crosses with random gaps, applies a “smile” curve (edges lifted on desktop, center dropped on mobile), randomly skips some for sparsity, and flips them vertically so they hang point-up: 

const hangRow = logoRowOffset + LOGO_ROWS + 1;
placeCrossesInRegion(1, totalCols - 1, { flip: true, anchorRow: hangRow });

Each placed cross's 1 cells are “carved” into a Map keyed by grid position, tagged with a tier (0–3) that selects a texture density. Overlapping crosses keep the lower (denser) tier.

computed, but not currently painted

The cross grid and the surrounding @ field are fully built — but the render loop skips them. The very first lines of the per-frame draw are: 

if (cell.isSpace) continue;
if (cell.isOuterFiller || cell.isCrossTexture) continue;

So spaces, filler, and cross cells never draw. What you actually see on screen is the logo bitmap glyphs alone, flying in against pure black. The cross/field machinery is scaffolding from an earlier, busier composition — left in place, currently dormant. If you want the field back, that's the line to loosen.

05 rounding the block's corners

The bitmap is a hard rectangle. To soften it, inBlockCornerCut(r, c) tests whether a cell sits inside one of the four corner squares but outside the rounding arc of radius boxCornerR (8/10/12 by tier). Those corner cells are reclassified as outer filler — and since filler isn't painted, the corners simply read as black. The result is a rounded slab of ASCII instead of a sharp box. 

if (r < boxTop + R && c < boxLeft + R) {          // top-left corner zone
  const dr = (boxTop + R) - r, dc = (boxLeft + R) - c;
  if (dr*dr + dc*dc > R*R) return true;          // outside the arc → cut it
}

06 the fly-in: timing

Once the grid is built, assignTiming() gives every cell a startAt time and a random launch angle. The cells are sorted by a key biased toward bottom rows first, with jitter, then spread evenly across a SWEEP_DURATION of 2.2 s: 

const sortKey = -cell.row * 1.5 + cell.col * 0.05 + Math.random() * 8;
...
c.startAt = (i / n) * SWEEP_DURATION + Math.random() * 40;

So the logo doesn't appear at once — it sweeps in, roughly from the bottom up, over a couple of seconds. Each individual cell, once its turn comes, falls into place over FALL_DURATION = 260 ms.

07 the render loop

loop(now) runs every animation frame. It clears to black, then for each paintable cell (logo glyphs only) computes where it is in its little life cycle:

  1. Off-screen start. The cell's target is its grid position. Its start point is that target pushed out along its random angle by ~1.2× the screen diagonal — so it begins well off-screen in some direction.
  2. Fall in. Progress fallT runs 0→1 over 260 ms, eased with easeOutCubic so it decelerates into place. Position lerps from start to target.
  3. Streak. While in flight it draws a short 3-step trailing streak behind itself in translucent red — the “meteor” tail.
  4. Flash. In flight the glyph is hot pink-white (rgba(255,180,180,.95)).
  5. Land & cool. After landing it glows from red toward bone-white over the next 500 ms (glow 0→1).

Once settled, two idle effects keep it alive:

  • Shutter flicker — deep-fill cells occasionally swap to a different filler glyph, each on its own sine phase/rate so they don't blink in sync. Gives the solid mass a crawling-static texture.
  • Yellow flutter — ~30% of deep-fill cells are eligible to randomly flare yellow (rgba(255,220,0,…)) on a slow noise function, like embers glinting inside the skull.

The loop never stops; after everything has landed it just keeps drawing the settled state with its flicker and flutter.

08 resize & replay

Resizing changes cell math, so the whole grid is rebuilt. To avoid a janky live reflow, a resize blacks the canvas immediately, debounces 250 ms, then replays the entire fly-in from scratch. Orientation changes do the same. (Internally startInstant() exists to rebuild without the animation, by backdating animStart so every cell reads as already-landed.)

09 the fire strips

Independent of the logo, two thin canvases run the classic Doom PSX fire algorithm. Each is a small 220×50 pixel buffer:

  • The bottom row is seeded to the hottest palette index (white).
  • spreadFire() propagates each pixel upward into a cell offset by a random −1/0/+1, subtracting a random decay — doubled in the top half so the flame thins as it rises.
  • A 37-stop palette ramps deep purple → magenta → pink → white, giving it the sickly cemetery glow rather than orange.
  • The seed row is re-randomized every 40 ms so the base flickers.

#fire-top is the same effect CSS-flipped (transform: scaleY(-1)) so it burns downward from under the navbar; #fire-bottom burns up from the footer.

10 the audio

The footer toggle (♪ off) drives two <audio> tracks, intro and terrorvoid. They auto-cycle: each plays for CYCLE_MS = 30 s, with a 3 s cross-fade between them, capped at a low MAX_VOL = 0.15. A small fade() helper ramps volume on requestAnimationFrame and cancels any in-flight fade on the same element (via a WeakMap token) so overlapping prev/next presses don't fight. Prev/next buttons jump tracks with the same cross-fade.

autoplay is opt-in by design

Nothing plays until you click the toggle — browsers block autoplay with sound, and this respects that. The toggle is the user gesture that unlocks it.

11 what actually ends up on screen

To cut through all the machinery, the live picture is:

  • An ASCII skull (the large bitmap, rounded corners) assembling itself from the bottom up over ~2 s, each glyph streaking in red and cooling to white.
  • The solid interior of the skull shimmering — static crawl plus occasional yellow ember flares.
  • Purple pixel-fire bleeding in from the top and bottom edges.
  • Optional doom ambience once you hit the toggle.
  • Everything replays on resize / rotate.

The cross field and the surrounding @ texture are built but not painted (see §04) — worth knowing if you ever wonder why all that code doesn't seem to show up.
